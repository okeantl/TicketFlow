# TicketFlow

Бэкенд сервиса бронирования билетов на концерты и в кино. Пользователь выбирает место, держит его 5 минут, оформляет заказ, оплата обрабатывается асинхронно в отдельном воркере, после оплаты приходит "билет".

Основное, на чем я сосредоточился в проекте, это конкурентность: чтобы одно место нельзя было продать два раза, даже если много людей жмут на него одновременно, а воркер получает одно и то же сообщение повторно.

## Стек

- **FastAPI** (async) - API
- **PostgreSQL + SQLAlchemy 2.0** (async, psycopg3) + **Alembic** - основные данные и миграции
- **Redis** - временная бронь мест (ключ с TTL) и кеш событий
- **RabbitMQ** (aio-pika) - очереди на оплату и уведомления
- **Docker Compose** - все поднимается одной командой
- **structlog** - логи в JSON
- **pytest + testcontainers** - тесты на настоящих Postgres и Redis в контейнерах
- **GitHub Actions** - ruff, mypy, pytest, сборка образа

## Архитектура

Модульный монолит. Каждый модуль лежит в `src/modules/` и разбит на слои `router -> service -> schemas`:

```
src/
  core/        конфиг, подключения к БД/Redis/RabbitMQ, ошибки, логи, JWT
  models/      модели SQLAlchemy
  modules/
    catalog/   события и места
    auth/      регистрация, логин, JWT
    booking/   бронь места
    orders/    заказы
  worker/
    payment_consumer.py        воркер оплаты
    notification_consumer.py   воркер уведомлений
```

Ошибки бизнес-логики - это свои исключения (`NotFoundError`, `AlreadyExistsError` и т.д. в `core/exceptions.py`), которые обрабатываются в одном месте в `main.py`, а не через `HTTPException` по всему коду.

Как проходит покупка:

```
POST /seats/{id}/hold        -> ключ seat_lock:{id} в Redis на 5 минут
POST /orders                 -> заказ PENDING в БД -> сообщение в очередь payment.process
payment-worker               -> оплата (заглушка) -> заказ PAID/FAILED, место SOLD
                             -> сообщение в notification.send_ticket
notification-worker          -> "отправляет" билет (пишет в лог)
```

## Как решены проблемы с конкурентностью

**Бронь места.** Бронь хранится только в Redis через `SET key value NX EX 300`. `NX` значит, что ключ ставится только если его еще нет, это атомарно, поэтому из нескольких одновременных запросов место получит только один. Статус HELD в базу не пишу. Раньше писал, и из-за этого места навсегда зависали в HELD, когда бронь истекала: Redis ключ удалял сам, а в базе статус так и оставался. Теперь в базе только AVAILABLE/SOLD, а "held" считается по наличию ключа в Redis.

**Два заказа на одно место.** В `create_order` строки мест блокируются через `SELECT ... FOR UPDATE`, и под этой блокировкой проверяется, нет ли уже заказа PENDING или PAID на это место. Без блокировки два параллельных запроса оба бы прошли проверку. id мест перед этим дедуплицируются и сортируются, чтобы не было двойной цены за `[5, 5]` и чтобы два запроса не заблокировали друг друга (deadlock), беря места в разном порядке.

**Повторная обработка оплаты.** RabbitMQ гарантирует доставку at-least-once, то есть одно сообщение может прийти два раза (например если воркер упал до ack). Поэтому воркер берет заказ через `FOR UPDATE` и работает только с заказом в статусе PENDING, остальные пропускает. Плюс отдельная проверка, что место еще не SOLD, перед тем как "списывать деньги".

**Снятие брони.** После оплаты (успешной или нет) воркер снимает Redis-локи, но только свои: в значении ключа лежит id пользователя, и удаление идет через Lua-скрипт, который сравнивает значение и удаляет ключ за одну операцию. Иначе, если бронь успела истечь и место взял другой человек, воркер удалил бы чужую бронь. Локи снимаются только после commit в БД.

**Ошибки в воркере.** ack вызывается в `finally`, чтобы сообщение не зависало неподтвержденным. Битые сообщения (невалидный JSON, нет order_id) сразу уходят в DLQ `payment.process.dlq`, ретраить их смысла нет. Остальные ошибки (упала БД, брокер) ретраятся до 3 раз через счетчик в заголовке `x-retry-count`, потом тоже в DLQ.

### Что я бы сделал иначе с настоящей платежкой

Сейчас оплата это заглушка `random()`, и блокировка заказа держится, пока она идет. С реальным платежным шлюзом это плохо: запрос может идти несколько секунд, все это время занято соединение с БД. И главное, если деньги списались, а воркер упал до commit, то после повтора спишутся второй раз, потому что транзакцию в базе откатить можно, а списание в банке нет. Правильно было бы сделать промежуточный статус PROCESSING (короткие транзакции до и после вызова шлюза) и передавать в шлюз idempotency key (например order_id), чтобы он сам не списывал дважды.

## API

| Метод | Путь | Авторизация | Что делает |
|---|---|---|---|
| POST | `/auth/register` | - | регистрация |
| POST | `/auth/login` | - | логин, возвращает JWT |
| GET | `/auth/me` | да | текущий пользователь |
| GET | `/events/` | - | список событий |
| GET | `/events/{event_id}` | - | событие (кешируется в Redis на 60 сек) |
| GET | `/events/{event_id}/seats` | - | места события со статусом available/held/sold |
| POST | `/seats/{seat_id}/hold` | да | забронировать место на 5 минут |
| POST | `/orders/` | да | создать заказ на свои забронированные места |
| GET | `/orders/{order_id}` | да | статус своего заказа |
| GET | `/health` | - | проверка Postgres, Redis, RabbitMQ |

Swagger: http://localhost:8000/docs

## Запуск

Нужен Docker.

```bash
cp .env.example .env
# в .env поменять пароли и сгенерировать SECRET_KEY:
# python -c "import secrets; print(secrets.token_hex(32))"

docker-compose up -d --build
docker-compose run --rm api alembic upgrade head
```

Поднимутся api (порт 8000), payment-worker, notification-worker, Postgres (5432), Redis (6379), RabbitMQ (5672, админка на 15672).

Ручки для создания событий пока нет, тестовые данные можно добавить через psql:

```bash
docker-compose exec postgres psql -U postgres -d polniikyrs
```

```sql
INSERT INTO events (title, description, starts_at) VALUES ('Концерт', 'тест', '2026-12-01 19:00');
INSERT INTO seats (event_id, row, number, status, price) VALUES
  (1, 'A', 1, 'AVAILABLE', 50.00),
  (1, 'A', 2, 'AVAILABLE', 50.00);
```

## Тесты

```bash
pip install -r requirements.txt
pytest
```

Для тестов тоже нужен запущенный Docker: testcontainers поднимает отдельные Postgres и Redis, миграции накатываются автоматически.

Что проверяется:
- 10 параллельных запросов на бронь одного места, у каждого своя сессия БД. Успешен ровно один, лок в Redis принадлежит ему, в базе место не изменилось
- регистрация и ошибка при повторном email
- миграции создают все таблицы
